## 1. Что такое PhoneBridge (кратко)

PC становится беспроводной гарнитурой для Android-телефона:
- **Медиа-звук** (YouTube/игры/музыка) — Android → PC через `MediaProjection` (`AudioPlaybackCaptureConfiguration`, usage MEDIA/GAME/UNKNOWN) → Opus/UDP → PC.
- **Микрофон PC → телефон** — обратный Opus/UDP-поток (для медиа, не для звонков).
- **Звонки** — **НЕ через приложение**. Аудио звонка идёт нативным Bluetooth Classic HFP:
  телефон = Audio Gateway, PC = Hands-Free unit. Работает "из коробки" ОС, если Bluetooth-адаптер
  PC поддерживает HFP-клиент (не все адаптеры это умеют — см. раздел 4).
  Приложение отвечает только за **control-plane**: показ входящего звонка/номера и
  `answer()/reject()` через Android `InCallService`/Telecom API, транслируемые на PC по
  WebSocket-сигналингу.
- Discovery — BLE advertising (телефон отдаёт IP+порт в manufacturer data) + ручной fallback.
- Опционально — AirPlay-приём для iPhone (media-only, звонки с iPhone недостижимы).

Стек: `android/` — Kotlin + Jetpack Compose; `pc/` — Rust (tokio, cpal, opus, btleplug,
tokio-tungstenite). Лицензия MIT, без облака, без телеметрии — только локальная сеть/Bluetooth.

## 2. Текущее состояние GUI в репозитории (реально в коде, не в README)

### Android (`android/app/src/main/java/com/phonebridge/app/`)
- `MainActivity.kt` — один экран Compose (`MainScreen`): заголовок, подзаголовок, кнопки
  "Start Bridge" / "Stop". Запрашивает permissions одним батчем, дальше — Toast.
  Нет: экрана статуса подключения, списка найденных PC, индикации звонка, настроек.
- Тема (`ui/theme/`) есть, но используется только для двух кнопок.

### Windows (`pc/src/ui/tray.rs`)
- Работает **только под Windows** (`#[cfg(target_os = "windows")]` в `ui/mod.rs`).
- Библиотека `tray-icon` — системный трей с меню: Answer Call / End Call / Mute Mic /
  Settings... / Quit. Пункт "Settings..." никуда не ведёт — окна настроек не существует.
- `notify()` сейчас просто пишет в лог (`log::info!`), реальных toast-уведомлений нет.

### macOS / Linux (`pc/src/ui/tray_stub.rs`)
- **Полный no-op.** `poll()` возвращает пустой список, `notify()` ничего не делает.
  На macOS и Linux у приложения **нет вообще никакого интерфейса** — только консольный лог.

Это и есть отправная точка. GUI для трёх из четырёх целевых поверхностей (macOS, Linux,
и полноценный Android UI) по факту не существует.

## 3. Задача для Kimi

Спроектировать единую GUI-архитектуру для всех платформ, с общим визуальным языком
и одинаковым набором экранов/состояний, учитывая асимметрию платформ (см. раздел 4).

### 3.1 Экраны/состояния, которые должны быть на **каждой** десктоп-платформе (Win/macOS/Linux)

1. **Первый запуск / pairing wizard**
   - Шаг 1: проверка Bluetooth-адаптера на поддержку HFP-клиента (см. 4.1) → явное
     предупреждение, если не поддерживается, с объяснением, что звонки работать не будут.
   - Шаг 2: инструкция включить Wi-Fi hotspot / подключить телефон к общей сети.
   - Шаг 3: BLE-discovery телефона (или ручной ввод IP как fallback) — статус поиска.
   - Шаг 4: инструкция включить на телефоне переключатель "Calls"/"Phone audio" в
     Bluetooth-паринге с этим ПК.
   - Шаг 5: подтверждение — все каналы (WS сигналинг, UDP медиа, BT HFP) активны.
2. **Главный экран/дашборд** (открывается по клику на трей-иконку или отдельным окном):
   - статус подключения (Connected / Reconnecting / Offline), имя телефона, IP.
   - переключатели: медиа-стрим вкл/выкл, микрофон ПК → телефон вкл/выкл.
   - индикатор состояния Bluetooth HFP (поддерживается/активен/не поддерживается).
3. **Incoming call overlay** — всплывающее уведомление с номером/именем и кнопками
   Answer/Decline, независимо от того, открыт дашборд или нет.
4. **Settings** — битрейт Opus, выбор аудиоустройств ввода/вывода на ПК, автозапуск,
   ручной ввод IP телефона (fallback без BLE), ссылка на диагностику Bluetooth-адаптера.
5. **Диагностика/логи** — простая читаемая панель для report'а проблем (адаптер без
   HFP, потеря UDP-пакетов, WS-дисконнект) — это то, что реально будет ломаться у людей.

### 3.2 Экраны на Android

1. Онбординг: запрос permissions с объяснением **зачем** каждое разрешение нужно
   (сейчас это один непрозрачный батч — это надо разбить и объяснить пользователю).
2. Главный экран: статус подключения к ПК, найденные/сохранённые ПК, кнопка Start/Stop,
   переключатели медиа/микрофона.
3. Инструкция/чеклист по включению Bluetooth "Calls" toggle для конкретного ПК
   (это шаг вне приложения, в системных Bluetooth-настройках — приложение должно
   на это явно наводить, иначе пользователь не поймёт, почему звонки не работают).
4. Экран настроек (битрейт, ручной IP, список сопряжённых ПК).

## 4. Ограничения и факты, которые нельзя игнорировать при проектировании UI

### 4.1 Bluetooth HFP — зависимость от железа/драйвера ПК
Работоспособность звонков зависит от того, поддерживает ли Bluetooth-адаптер ПК роль
Hands-Free Unit (клиент HFP). Это системная/драйверная возможность, приложение
**не может** её добавить программно. UI обязан:
- проверять и явно показывать этот статус (по возможности — программно через
  Windows Bluetooth API / BlueZ на Linux / CoreBluetooth на macOS; если программной
  проверки нет — дать пользователю инструкцию проверить вручную);
- не молчать, если HFP недоступен — это самая частая причина "не работает" у Phone Link
  и она же будет у нас.

### 4.2 Асимметрия платформ
- Windows уже имеет частичную реализацию (`tray.rs`, крейт `tray-icon`) — **не переписывать
  с нуля**, расширять.
- macOS/Linux — с нуля. Нужно выбрать кросс-платформенный (или platform-specific) toolkit
  для Rust-трея + окна настроек. Варианты для сравнения и обоснованного выбора:
  `tray-icon` (уже используется на Windows — проверить, действительно ли кросс-платформенный
  для трея, чтобы не плодить два разных API) + окно настроек через `egui`/`eframe`
  (лёгкий, self-contained) или `iced`. Обосновать выбор с точки зрения: размер бинаря,
  нативность вида, сложность интеграции с существующим `tokio`-рантаймом в `main.rs`.
- iPhone не поддерживает звонки в принципе (см. раздел 1) — в Android GUI это не
  относится, но если будет отдельный iOS-клиент в будущем, его тут не проектируем.

### 4.3 Repo drift
Ты (Kimi) и Claude периодически откатываете правки друг друга по одним и тем же файлам.
Договорённость: каждый файл, который меняешь, отдавай **полной заменой** (как в
`apply_final.sh`), а не патчем/диффом, и перечисляй в конце ответа полный список
затронутых файлов. Если меняешь `pc/src/ui/mod.rs`/`tray.rs` — не удаляй и не упрощай
уже работающий Windows-трей.

## 5. Формат ответа, который нужен от Kimi

Для каждой из 4 платформ (Android, Windows, macOS, Linux):
1. Выбор технологии/библиотеки для GUI (для десктопа — с явным сравнением 2-3 вариантов
   и обоснованием, не просто "возьмём X").
2. Список экранов из раздела 3 → дерево компонентов/файлов, которые нужно добавить
   в существующую структуру репозитория (пути внутри `android/.../ui/` и `pc/src/ui/`).
3. Подход к управлению состоянием (для Compose — `StateFlow`/`ViewModel`; для Rust —
   как стыкуется с уже существующим `Arc<Mutex<SharedState>>` и `tokio::spawn`-задачами
   в `main.rs`, чтобы не блокировать аудио-пайплайн UI-потоком).
4. Как UI получает статус HFP-адаптера и события "входящий звонок" — через какой канал
   (в `SharedState`/`protocol::mod.rs` уже есть заготовка — использовать её, не городить
   отдельный канал).
5. Полный код файлов (не диффы), плюс итоговый список изменённых/добавленных файлов.

Если для какого-то пункта не хватает контекста из репозитория — сначала запросить
конкретный файл, а не додумывать API, которого нет в проекте.
