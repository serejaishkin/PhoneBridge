## Что НЕ сделано (по приоритету)

1. **TLS-клиент на Android**, который реально подключается к `PairingServer` на PC,
   шлёт `Hello`, получает `HelloAck`, и на основании short_code запрашивает у
   пользователя подтверждение пейринга. Сейчас на Android есть `Identity`/`TrustStore`,
   но нет кода, который открывает TLS-сокет к найденному через `DiscoveryClient` PC.
   **Это следующий шаг №1** — без него пейринг не замкнут в кольцо.

2. **Реальная детекция поддержки Bluetooth HFP на PC** (была честная заглушка,
   всегда `Unknown`). Три платформенные реализации:
   - [x] Windows — через WinRT: наличие адаптера + BR/EDR, затем список
     кэшированных RFCOMM-сервисов сопряжённых устройств; найден Hands-Free
     (111E) → Supported (2026-08-26, `pc/src/call/hfp_windows.rs`).
   - [x] Linux — через BlueZ D-Bus (`zbus`): GetManagedObjects → адаптеры hciX,
     у каждого Adapter1.UUIDs ищем 111E/111F. Код проверен компиляцией модуля
     против реального zbus 5.19, но НЕ запускался на живом Linux — прогнать на
     машине с BlueZ (2026-08-26, `pc/src/call/hfp_linux.rs`).
   - [x] macOS — через IOBluetooth (`objc2-io-bluetooth`): контроллер есть →
     Supported (у Apple стек HFP-capable всегда), нет → Unsupported. Модуль
     проверен компиляцией под aarch64-apple-darwin, живой запуск на Mac не
     выполнялся (2026-08-26, `pc/src/call/hfp_macos.rs`).

3. **GUI** — см. `AI_HANDOFF_GUI.md`. Прогресс 2026-08-26: eframe-GUI работает
   на всех трёх десктопах; системный трей восстановлен (он осиротел после
   перехода на eframe) для Windows и macOS через `tray-icon` внутри
   creator-closure главного потока; на Linux трей отложен — backend tray-icon
   требует GTK main loop, конфликтующий с winit в главном потоке (на Linux
   интерфейс пока даёт окно eframe).
   Готовых простых системных API "поддерживает ли адаптер HFP client role" нет
   ни на одной платформе — вероятно, придётся определять по факту через список
   поддерживаемых профилей уже сопряжённого устройства, а не абстрактно у адаптера.

3. **GUI** — см. `AI_HANDOFF_GUI.md`, он не потерял актуальность, только теперь
   есть реальный `UiBackend`-трейт (`pc/src/ui/mod.rs`), под который писать
   `WindowsUi`/`LinuxUi`/`MacUi`, вместо абстрактного описания. На Android —
   `OnboardingStep.kt` уже даёт модель шагов, экраны под неё не написаны.

4. **Медиа-аудио** (Opus/UDP-стрим music/game) — из этого скелета сознательно
   выкинуто, потому что это отдельный, гораздо более простой и уже понятный
   кусок (он был рабочим прототипом в PhoneBridge v1, `AudioCaptureService.kt`/
   `AudioPlaybackCaptureConfiguration`). Его можно перенести из v1 почти как есть,
   не переписывая — там проблем архитектурно не было, в отличие от звонков.

5. **Реальная сборка Android-части** и первый end-to-end тест на двух устройствах —
   ничего в этом скелете не проверялось вживую, только code review + компиляция

## Известные слабые места в текущем скелете (честно)

- ~~В `pairing/server.rs` fingerprint клиента пока не сверяется по-настоящему~~
  **Исправлено полностью 2026-08-26 — взаимный TLS**: телефон обязан предъявить
  сертификат в самом handshake (`X509KeyManager` на Android, кастомный
  `ClientCertVerifier` на PC), fingerprint берётся из согласованной TLS-сессии и
  сверяется с заявленным в Hello; доверенная пара (device_id, fingerprint)
  сохраняется в TrustStore после Allow/Reject-диалога с short_code; TOFU-пин
  сертификата PC по хосту с перекрёстной сверкой по `HelloAck`. Весь конвейер
  покрыт интеграционными тестами на PC-стороне (включая отказ клиента без
  сертификата). Осталось: собрать Android и прогнать пейринг на живой паре устройств.
- Kotlin-сторона протокола (`Protocol.kt`) не протестирована на побайтовое
  совпадение JSON с Rust-стороной (`serde` с `tag`/`content` vs kotlinx.serialization
  polymorphic) — см. предупреждение в конце файла. Первое, что стоит сделать
  при запуске — залогировать сырые JSON-строки с обеих сторон и сверить руками.
- `Cargo.toml` пестрит точными пинами версий (`=0.23.5`, `=1.7.0` и т.д.) из-за
  cargo 1.75 в этом окружении и `edition2024` у новых версий транзитивных
  зависимостей. На машине с более новым cargo эти пины стоит пересмотреть —
  не обязательно тащить именно эти старые версии дальше.
